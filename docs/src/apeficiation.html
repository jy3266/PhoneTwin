2. Apeficiation 저장소 분석

저장소는 2026-11-04에 올라온 커밋 5개(마지막 5ef05a3 “firmware → arduino, gateway → pi 폴더 이름 변경”) 이후 바뀌지 않았습니다. 파일은 3개, 합계 857줄입니다.

2-2. 거리 측정 방식 (비대칭 양방향 거리 측정)

비행시간(ToF) = (round1 × round2 − reply1 × reply2) ÷ (round1 + round2 + reply1 + reply2). 두 기기의 시계가 서로 맞지 않아도 되는 방식입니다. 거리 = ToF × 빛의 속도.

데이터 (18바이트)내용
[0]종류: 0 POLL · 1 POLL_ACK · 2 RANGE · 3 RANGE_REPORT · 255 RANGE_FAILED
[1..15]RANGE: 태그 시각 3개(5바이트씩 [1] [6] [11]) · RANGE_REPORT: 거리 float [1..4]
[16] / [17]받을 앵커 번호(다른 앵커는 무시) / 스윕 번호(0~255 반복)

2-3. 위치 계산과 파이의 처리 순서

#단계원본 동작 (pi_gateway.py)
1줄 읽기모든 /dev/ttyACM*를 115200bps로 동시에 읽고, 정규식 ^R,(\d+),(\d+),(-?\d+\.\d+),(-?\d+\.\d+)$에 맞는 줄만 사용
2스윕 모으기스윕 번호별로 모아 앵커 4개가 모두 오면 계산. 0.5초 안에 다 안 모이면 버림. 거리가 0~6m 밖이면 버림
3튐 제거앵커별 최근 거리 3개의 중앙값
4위치 풀기앵커 1을 기준으로 거리 제곱의 차이를 빼서 1차식 3개로 만들고 크라메르 공식으로 x, y, z. 행렬식이 0에 가까우면 실패
5부드럽게새 위치 × 0.4 + 예전 위치 × 0.6. 1초 넘게 끊겼으면 새로 시작
6보내기OSC /tag/position [x×100, y×100, z×100] (float 3개, cm) → 기본 127.0.0.1:8000

앵커 좌표(ANCHOR_POS)는 태그 펌웨어와 파이 코드 두 곳에 같은 값으로 적혀 있습니다: 1 (0, 0, 0.5) · 2 (3, 0, 2.5) · 3 (0, 3, 2.5) · 4 (3, 3, 0.5) m — 원본 주석에 “임시 값”이라고 되어 있습니다.

2-4. 우리 시스템에 붙일 때 문제가 되는 점

#문제영향과 이번 대응
1좌표 원점 = 앵커 1이 있는 방 모서리스캔의 A·B와 무관해 그대로면 관객이 엉뚱한 곳에 나타남 → 언리얼 A·B 맞춤(키 7·8) 추가
2앵커 좌표가 코드에 고정(두 곳)실제 방에 맞게 팀이 펌웨어와 파이 양쪽을 같은 값으로 고쳐야 함. 앵커 4개 높이가 같으면 위치가 하나도 안 나옴(시뮬레이터 flat으로 확인)
34개가 모두 와야 계산사람이 앵커 하나를 가리면 그 스윕은 버려짐. 앵커당 10%만 실패해도 출력이 28 → 12번/초(시뮬레이터 dropout)
4방향·품질 정보 없음위치만 옴 → 언리얼이 걷는 방향으로 바라보게 함. HUD에 원 좌표 표시
5진동이 언리얼과 무관원본 태그는 정해진 리듬(모터마다 약 2.6초 동안 서서히 세졌다가 0.5초 최대, 다시 2.6초 동안 약해진 뒤 22.5초 쉼. 모터 5개가 5.6초씩 엇갈려 시작). 거리별 진동은 PhoneTwin 버전 필요
6보낼 주소 기본값 127.0.0.1파이 자기 자신 → 실행할 때 --osc-host <PC IP> 필수

3. 사용법 A — 하드웨어 없이 시험

PC 한 대로 “앵커 4개 → 파이 → 언리얼” 전체를 재현합니다. 앵커가 USB로 내보내는 줄만 가짜이고, 위치 계산과 OSC 전송은 원본 pi_gateway.py가 그대로 합니다. 실행할 때마다 GitHub에서 최신 원본을 받아 오므로 팀이 코드를 고치면 그 버전으로 시험됩니다.

준비 (처음 한 번)

  • 파이썬(py)과 git이 있으면 됩니다. pyserial·python-osc는 없어도 됩니다(시뮬레이터가 같은 바이트의 OSC를 직접 만듦).
  • 원본은 PhoneTwin_v4/tools/.apeficiation/에 자동으로 받아지며 git에는 올라가지 않습니다(팀 코드라 다시 배포하지 않음).

언리얼과 함께 확인하기

  1. 언리얼 에디터를 켜고 Play. 키 2를 눌러 입력을 “UWB 태그”로 바꿉니다.
  2. PowerShell에서 PhoneTwin_v4 폴더로 가서 실행합니다. 
    py tools\apeficiation_sim.py --walk ab
  3. 0~6초: 가짜 태그가 A 위에 서 있습니다 → 언리얼에서 7.
    6~12초: B 위 → 8. HUD에 “UWB A·B 맞춤 완료 · A→B 실측 1.00 m” 정도가 뜹니다.
  4. 그 뒤로 가짜 관객이 8자로 걷습니다. 점구름 위에서 관객이 움직이고, 사물에 다가가면 소리·물결이 나는지 봅니다.
  5. 끝내려면 PowerShell에서 Ctrl+C. 맞춘 A·B는 저장되므로 다음부터는 7·8 없이 py tools\apeficiation_sim.py만 실행해도 됩니다.

6가지 상황

이름재현하는 것보이는 결과 (자체 시험 기준)
ideal오차 없는 거리오차 평균 3cm — 원본의 부드럽게 처리(0.4)로 생기는 지연뿐
noisy거리 잡음 5cm (기본값)오차 평균 5cm, 95% 8cm
uncal안테나 지연 미보정 → 모든 거리 +25cm오차 평균 10cm, 잔차 23cm ← 실제 장비에서 잔차가 크면 보정이 필요하다는 신호
dropout앵커 응답이 10%씩 실패(몸이 가림)스윕의 35%가 버려지고 출력 28 → 12번/초
spikes5% 확률로 반사파 +1.5m중앙값 필터가 대부분 막지만 최대 70cm 튐
flat앵커 4개 높이가 모두 1.5m위치 0개 — 원본 계산식의 한계(높이를 다르게 둬야 함)

4. 사용법 B — 실제 장비 연결

팀(하드웨어)이 할 일

  1. 앵커 위치 정하기: 방 안 아무 곳이나 가능하지만 높이를 서로 다르게(예: 두 개는 0.5m, 두 개는 2.5m). 앵커 1의 바닥 위치가 원점, 1→2가 +x, 1→3 쪽이 +y가 되도록 실제 좌표를 m로 잽니다.
  2. 그 좌표를 uwb_tag_motors.ino와 pi_gateway.py의 ANCHOR_POS 두 곳 모두에 같은 값으로 적고, 태그·앵커 1~4에 업로드(ANCHOR_ID 1~4).
  3. 앵커 4개를 USB로 파이에 연결. 태그를 켜고 LED가 초록으로 깜빡이는지 확인.
  4. 파이에서 먼저 출력만 확인한 뒤 PC로 보냅니다. 
    python3 pi_gateway.py --dry-run                    # x,y,z (m) 와 residual 이 계속 나오면 정상
python3 pi_gateway.py --osc-host 192.168.0.12      # 언리얼 PC의 IP (PowerShell: ipconfig)

언리얼에서 할 일

  1. 처음 한 번: Windows 방화벽이 UnrealEditor의 UDP 수신을 묻으면 “허용”. 이미 막았다면 방화벽 설정에서 UnrealEditor를 허용 목록에 추가(포트 8000).
  2. Play → 2. HUD 두 번째 줄이 “UWB 태그 (Pi OSC): 파이 IP · 추적 중”, 그 아래 “UWB 원 좌표 (…) m · Apeficiation 게이트웨이 형식”이면 수신 중.
  3. 태그를 스캔 바닥 A(휴대폰 앱 3D 화면의 초록 표시, 바닥 정중앙) 위에 1초 이상 가만히 두고 7.
  4. 태그를 B(파랑, A에서 1m) 위에 두고 8 → “UWB A·B 맞춤 완료 · A→B 실측 x m”. 실측이 1m에서 많이 벗어나면 앵커 좌표나 보정을 다시 봅니다.

5. 기술 — 언리얼이 OSC를 받는 방식

5-1. 처리 흐름 (PhoneTwinLink 플러그인)

#코드하는 일
1OpenSocket()Play 시 UDP 7777(휴대폰)과 별도로 UDP 8000 소켓(UwbSocket)을 엶. 포트를 이미 다른 프로그램이 쓰면 로그에 오류
2ReceiveUwbOsc()매 프레임 쌓인 패킷을 모두 읽음
3PhoneTwin::ParseOscPacket()OSC 1.0 메시지·번들(중첩 포함) 해석. float/int/double/문자열 인자. 잘린 패킷은 버림
4HandleUwbOsc()/tag/position: × UwbOscMetresPerUnit(0.01) → 원 좌표 m(UwbRaw), 최근 2초 기록 → FUwbMarks::ToRoom() → 방 좌표 R(EspPose). 방향이 1초 넘게 안 오면 걷는 방향으로 yaw. 보낸 쪽 IP를 진동 응답 주소로 기억
5UpdateTracker()R(m) → 언리얼(cm): TrackerPos = EspOrigin + Yaw(EspYawOffset) · (x, −y, z) × 100 × EspScale. 스캔은 meta의 A=원점, A→B=+X로 놓여 있어 그대로 겹침
6Measure(), UpdateSounds()사물·표면까지 거리, 소리, 닿을 때 물결, 진동 세기(PTH1 → 보낸 IP:4210, 원본 파이는 무시)

0.5초(SignalTimeout) 동안 위치가 안 오면 “끊김”으로 보고 추적을 멈춥니다. 원본은 스윕이 불완전하면 아무것도 안 보내므로 이 시간으로 끊김을 판단합니다.

5-2. A·B 맞춤 식 (PhoneTwin::FUwbMarks, PhoneTwinCore.h)

θ = atan2(B.y − A.y, B.x − A.x)      ← 원본 좌표에서 A→B 방향
dx = x − A.x,   dy = y − A.y
X =  cosθ·dx + sinθ·dy               ← 앞 (A→B 방향 성분)
Y = −sinθ·dx + cosθ·dy               ← 왼쪽
Z =  z
bUwbMirror 켜짐: 계산 전에 원본 y, A.y, B.y의 부호를 바꿈 (좌우 반전)
방향: yaw_R = yaw_원본 − θ  (반전이면 −yaw_원본 − θ)

A는 7을 누른 순간부터 거슬러 1초 동안 받은 위치의 평균(3개 이상 필요), B도 같습니다. A–B가 30cm보다 가까우면 거부합니다. 결과는 ARKO_PROJECT/PhoneTwinScans/uwb_frame.json에 저장되고 Play할 때마다 읽습니다.

{
  "note": "UWB OSC gateway frame (m) at the scan floor marks A and B, written by Unreal keys 7/8",
  "a": [1.0000, 1.5000, 1.0000],
  "b": [2.0000, 1.5000, 1.0000]
}

PhoneTwin 게이트웨이(--mark A/B로 이미 R 좌표를 보냄)를 쓸 때는 언리얼 맞춤을 안 해도 되고, 해도 A≈(0,0), A→B≈+X가 기록되어 결과가 거의 같습니다.

5-3. 방향 추정

원본은 /tag/heading을 보내지 않으므로, 방향 메시지가 1초 넘게 없으면 언리얼이 직접 정합니다. 마지막 기준점에서 바닥 평면으로 UwbHeadingStepCm(15cm) 이상 움직이면 그 이동 방향을 yaw로 삼고 기준점을 옮깁니다. 제자리에 서 있으면 마지막 방향을 유지합니다. 소리의 “뒤돌아섬” 감쇠, 1인칭 시점이 이 방향을 씁니다.
